Found nine correctness issues, ordered by severity. These are static findings; I read both implementations, made no edits, and ran no builds or tests.

1. **Image-size arithmetic wraps before the limit check.** [link/layout.c:193](/home/exedev/bottom-up/link/layout.c:193), [link/layout.c:253](/home/exedev/bottom-up/link/layout.c:253). Both per-unit sizes and the running address use unchecked `u32` arithmetic. Two live 2 GiB BSS symbols in one unit/alignment class make its size sum wrap to zero; the final check at line 480 can then accept an image whose memory segment cannot contain those symbols. Overflow in file-backed buckets can additionally put writes outside the output mapping. This arithmetic hazard is inherited from Go.

2. **GC bitmap writes are not bounded by the symbol or bitmap size.** [link/write.c:154](/home/exedev/bottom-up/link/write.c:154). `gcSym` trusts every pointer-word index produced by the type descriptor. A data/BSS symbol whose associated type describes pointers beyond its allocated extent can overwrite another unit’s bitmap bytes—or memory outside the bitmap. Overlapping updates also invalidate the assumption that workers write disjoint bytes. Go checks the bitmap slice boundary; C has no corresponding check.

3. **Symbol-reference indices can escape the global arrays.** [link/common.h:314](/home/exedev/bottom-up/link/common.h:314). `oref` checks ordinary package indices but never checks symbol indices, including the direct `builtins[idx]` access. An out-of-range relocation or auxiliary reference can produce an invalid ID subsequently used to index `canon`, `addr`, or atomically update `state`. Smaller out-of-range indices can silently resolve into the next object instead of being rejected.

4. **Object-header validation does not validate the records subsequently accessed.** [link/load.c:49](/home/exedev/bottom-up/link/load.c:49), [link/common.h:268](/home/exedev/bottom-up/link/common.h:268). Monotonic block offsets within the input are insufficient: index-table lengths, individual data/string ranges, and relocation/auxiliary spans remain unchecked. An object containing definitions but a truncated index table passes loading and causes later accessors to read beyond the object; descending index entries also underflow their computed lengths. The object does not retain its length for later validation.

5. **FuncInfo decoding ignores its supplied length.** [link/dead.c:260](/home/exedev/bottom-up/link/dead.c:260). A live function with a nonempty but truncated FuncInfo reaches unconditional reads in `fiNumInl`; file and inline-node counts also drive unchecked pointer arithmetic. This can read past the mapping during reachability, before output generation. The corresponding Go FuncInfo reader uses bounds-checked slices.

6. **The missing-method relocation path writes more bytes than it validates.** [link/write.c:262](/home/exedev/bottom-up/link/write.c:262). The preceding bounds check uses the relocation’s declared width, but an unresolved `R_METHODOFF` unconditionally writes a four-byte sentinel. A malformed narrower relocation near a symbol’s end therefore overwrites its neighbor, potentially racing with another output worker. Go’s symbol-sized `P` slice prevents that write from crossing the symbol boundary.

7. **Typelink sorting trusts an unchecked decoded string length.** [link/layout.c:136](/home/exedev/bottom-up/link/layout.c:136). Unlike `nameData`, `typeString` does not check successful varint decoding or whether the declared name fits its data. A reachable typelink with truncated namedata can consequently make the sorting comparator’s `memcmp` read beyond the input mapping. The Go reference also has an unsafe-string hazard here; the C port retains it.

8. **Reachability mixes atomic writes with plain reads of shared state.** [link/common.h:361](/home/exedev/bottom-up/link/common.h:361). During a parallel flood, one worker can call `isDef(T)` while another executes `fmark(T)` or `setIface(T)`, atomically modifying the same `state[T]` word. Reading only the logically stable `stUndef` bit does not make the underlying plain load race-free. This is C undefined behavior on ordinary shared-reference graphs; the read needs the existing atomic-load helper. The Go reference contains the same access pattern.

9. **Exported-method detection uses different Unicode tables from Go.** [link/dead.c:438](/home/exedev/bottom-up/link/dead.c:438). `iswupper` uses the host libc’s tables, whereas this reference toolchain uses Unicode 17. For example, an exported method beginning with U+1C89 is recognized by Go but absent from this VM’s older libc tables. When reflection is the only reason to retain that method, C can prune its implementation while Go retains it, leaving reflection unable to call it correctly.
