1. **The write floor is optimistic for the implemented path.** [FLOOR.md:39](/home/exedev/bottom-up/FLOOR.md:39) budgets **4.92 ms**, counting each output byte once. Reuse first zeros the entire image, then copies symbols over it ([write.c:64](/home/exedev/bottom-up/link/write.c:64)). The extra **109.5 MB / 56.7 GB/s ≈ 1.93 ms** makes that model approximately **6.85 ms**, before page-management costs. Reach’s **2.78 ms** also assumes independent random-access throughput; the actual dependency chains face **157 ns/load** (`chase_512m = 6.37M/s`). That is a latency constraint, not enough evidence to invent a replacement whole-phase floor.

2. **Dependent metadata reads and repeated scans keep it away from the floor.** The flood follows index → relocations → target flags → canonical ID → flags; batches of **64** overlap those misses ([dead.c:493](/home/exedev/bottom-up/link/dead.c:493)). Layout still scans all definitions twice, instead of just live symbols ([layout.c:160](/home/exedev/bottom-up/link/layout.c:160)). **Yes, these are being attacked:** batching is implemented; [PLAN.md:71](/home/exedev/bottom-up/PLAN.md:71) targets live-only layout, unnecessary hash-size reads and excess population. Eliminating the full-image zero pass is not explicitly listed.

3. **The strongest scaling objection is rebuilding scattered metadata for every link.** Inputs grow from **5.2M slots / 842 MB** for MinIO to **13.2M / 1.97 GB** for kube-apiserver. More workers do not remove dependent accesses, page-table work or repeated full-slot scans. [STATUS.md:8](/home/exedev/bottom-up/STATUS.md:8) itself projects **35–45 ms**, missing its stated **21 ms** exit target. I would build a compact, partitioned symbol/adjacency representation, compact the live set once, then layout and emit from that. Any persistent archive index must include its construction cost in the cold campaign result.
