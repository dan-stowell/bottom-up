# CHARTER

Only the user edits this file. Agents read it at the start of every session. The current
campaign is in `PLAN.md`; the procedure is in `LOOP.md`.

*Draft of 2026-11-13, written for the user to edit.*

## North star

Bottom up: build a core that runs at hardware speed, then grow it to take on real workloads.
The score is how close each workload gets to what the machine can physically do, not how it
compares with existing tools. Start from Strand, the loop-free SIMD language in this repo
(README.md, DESIGN.md), and change it freely, or leave it where a measurement says to
(`SCALAR_LEDGER.md`).

Go deep on the compute-heavy parts of building a real program, narrow is fine: **linking**
first, then **code emission**. Lexing and parsing are about 1% of a compile's CPU; they are
not workloads here unless one of these needs them. The sibling project
`dan-stowell/simd-lang` attacks the same goal top down (a whole-program Go compiler, `fc`, and
its linker, `fclink`). The two meet in the middle, and neither stays away from work it needs.

## The one number: % of floor

Every report leads with `FLOOR.md`, regenerated by one script. One row per workload phase:

    workload/phase   bytes in   bytes out   ms (1 core)   ms (8 cores)   floor ms (8 cores)   % of floor

The floor comes from measured machine limits (`HARDWARE.md`, `hw/`): bytes moved over the
bandwidth of each level (DRAM, L3, L2, L1), and instructions per byte over cores x IPC x clock.
Say which limit binds. A change matters if it moves this table or the campaign's oracle number.
Microbenchmarks are diagnostics, never results.

## Correctness

Every workload is checked against the stock toolchain: a linked binary passes the program's
own tests and diffs section by section against `go tool link`'s output; emitted code matches
the Go assembler's bytes for the same input. Fuzz at chunk and core boundaries. Strand's
bootstrap fixed point and `./test.sh` stay green.

## Cold

Measure cold: inputs read after dropping the page cache
(`sync; echo 3 | sudo tee /proc/sys/vm/drop_caches`), nothing carried over between timed runs.
Report the warm number next to it.

## How to work

- **Never stop to ask.** Pick the most ambitious step you can justify, write why in
  `JOURNAL.md`, and do it. Decisions that are the user's go in STATUS.md; keep working.
- **Horizon.** This work runs for days. A session ending (usage limit, context, restart) is not
  an event; the next one continues from `PLAN.md`. Time left, usage left and "the next session"
  are never reasons to decline or shrink a step. The only valid reason is a measurement that
  shows it cannot pay.
- **Calibrate on your own record, not human estimates.** In the sibling project, a baseline code
  generator reached 97% of MinIO's functions in under an hour, a link spike came within 46 of
  the stock linker's 122,860 functions in 33 minutes, and a whole Go compiler passed the
  standard library's tests in about two days. A linker at hardware speed is days of work for
  you, not months.
- **One campaign at a time**, named in `PLAN.md` by the user. You decide how, not whether.
- **Negative results are results.** Write them up and move on.
- **Commit and push often** with real messages. Report **absolute numbers** (ms, GB/s),
  timestamps from `date -u`.
- **The host is noisy.** Compare configurations interleaved in the same window.

## Anti-goals

- Meta work: frameworks for finding speedups, benchmark harness polish.
- Wins that don't move FLOOR.md.
- Declining or shrinking work because of time left, usage, or a session ending.
